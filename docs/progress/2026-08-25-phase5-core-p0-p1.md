`simCode` is not exposed.

## Realtime boundary and schema

The integrated query path is:

`Controller -> existing DataScope -> VehicleLocationQueryService/TaskTrackQueryService
-> GpsInfluxService -> InfluxDB`

It does not call the development backend on port 18080. Existing development-only
track adapters now delegate to the shared `GpsInfluxService` query path instead of
building a second Flux schema. Their legacy HTTP controllers are explicitly `denyAll()`;
frontend integrations use only the scoped `/api/v1` contracts.

Confirmed schema:

- org: `smart_logistics`
- bucket: `gps_track`
- measurement: `vehicle_gps`
- tag: `vehicle_id`
- fields: `lat`, `lon`, `speed`, `direction`
- sample time: Influx `_time`
- mapping: MySQL `vehicle.sim_code` -> Influx `vehicle_id`

`Vehicle.simCode` was added to the entity mapping for the already-existing migration
`004_vehicle_sim_code.sql`. It is internal only.

## Historical GPS compatibility

Queries read raw `_field/_value/_time/vehicle_id` records and never pivot on exact
`_time`. Java reconstruction groups by vehicle, sorts timestamps and assigns a field
only to the nearest candidate which:

1. is inside the configurable `app.realtime.gps-merge-tolerance` window; and
2. does not already contain that field.

Only samples containing both lat and lon are returned. Missing coordinates and records
outside the tolerance are not paired or fabricated. Speed and direction remain nullable
when the historical source lacks those fields. Tests cover millisecond differences,
missing lat/lon, out-of-order input, consecutive samples and multiple vehicles.

REST contract, service boundary, RBAC/DataScope and mocked integration are complete.
Real InfluxDB end-to-end verification is pending.

## Ingestion follow-up

Historical compatibility does not correct future ingestion. The repository's current
MQTT writer still uses an older measurement/tag/field contract and does not persist
direction. A future teammate-owned correction should write one `vehicle_gps` Point per
GPS sample containing lat, lon, speed and direction with one timestamp. Phase 5 does not
silently rewrite that ingestion path.

The existing MQTT -> `/ws/vehicle-locations` broadcast remains unchanged. Public
WebSocket end-to-end verification is pending and is not an HTTP delivery blocker.

## RBAC and DataScope

- OWNER: own Cargo and Cargo-related Task/Vehicle location data only.
- DRIVER: assigned Vehicle and own/current Task/Cargo data only.
- WAREHOUSE_MANAGER: existing V1 simplified warehouse read scope; may delete eligible Cargo.
- DISPATCHER: existing V1 simplified dispatch read scope; Alarm mutation remains denied.
- ADMIN: read-all and Cargo base-data deletion; Task/Alarm mutation is not automatically granted.

Explicit out-of-scope Vehicle, Task and Cargo access uses the existing scoped-resource
403 behavior and never queries the realtime provider first.

## Cargo deletion and status records

Cargo deletion is a transactional physical delete because Cargo has no soft-delete
column. It is permitted only for `WAITING` Cargo with no active WAITING/TRANSPORTING
Task. Existing `cargo_item` foreign key `ON DELETE CASCADE` prevents orphan items.
Other historical foreign-key references may still produce a standard 409 conflict.

Migration `005_transport_task_status_record.sql` adds the smallest authoritative Task
transition history table. Every successful Task transition inserts a record in the same
transaction with task, cargo, from/to status, operator identity/role and change time.
Failed transitions do not create records. No old history is fabricated or backfilled.
The migration is required for status-record persistence and was not executed by Phase 5.

## Planned route decision

No route-point table, route provider or other real planned-route source exists. Therefore
`GET /api/v1/transport-tasks/{id}/planned-route` was not added. A straight line between
start/end was not fabricated. This is deferred pending a real route provider.

## ETA decision

Task detail exposes `estimatedArrivalTime`, but the repository has no authoritative writer,
remaining-distance source or ETA provider. Therefore Phase 5 does not claim that field is
a complete authoritative ETA contract and does not add `/eta` with a fabricated algorithm.
ETA integration is deferred pending one authoritative provider.
